# Run order — Phase 07

## 1. Establish the boundary

1. Name the repository and branch.
2. State what systems, data, and actions are out of scope.
3. Run the existing build, tests, AI projection check, and program check.
4. Record pre-existing failures separately.
5. Identify the authorized program owner and approver—or record that they are
   missing.

## 2. Orient to the program

6. Read the program index, map, contract, coverage matrix, and GRC map.
7. Walk the eight categories and explain why technical governance is a branch
   of the broader AI governance system.
8. Confirm every folder has a README and authority metadata.
9. Classify each current record as active, draft, proposal, course example,
   external terrain, or missing.
10. Review Full, Essential, and Light. Select a starting profile only after
    checking scope, risk, obligations, authority, and expansion triggers.

## 3. Run the product

11. Install and start `completed/apps/ai-program/`.
12. Verify the left navigation matches the selected folder profile.
13. Switch profiles and confirm navigation, findings, and advisor scope change
    without changing canonical policy.
14. Open one category and one nested node; compare the UI with its README.
15. Inspect overview scores and trace each result to exact findings.
16. Confirm the app never describes readiness as certification.

## 4. Ask and challenge

17. Ask all six canonical program-health questions plus “How is our AI
    culture?” and “Which program profile is active?”
18. For one answer, verify scope, sources, owner, freshness, exceptions or
    conflicts, uncertainty, and next action.
19. Ask a question the program cannot answer. Confirm absence is reported as a
    gap rather than permission.
20. Compare the application answer with the `ai-program-advisor` result.

## 5. Build one trace

21. Select an approved client requirement. If unavailable, use the fictional
    teaching record and visibly mark it non-policy.
22. Record source and approved interpretation authority.
23. Add scope, risk tier, rationale, control, enforcement, evidence, owner,
    approver, exception state, dates, and triggers.
24. Remove or invalidate one link temporarily; verify the system reports the
    affected restriction.
25. Restore the trace and record the verification result.

## 6. Propose and review

26. Select one exact finding.
27. Prepare a proposal in the application.
28. Add migration, validation, evidence, rollback, stop conditions, owner,
    approver, and review date.
29. Confirm no canonical file changed merely because the proposal was created.
30. Submit for the authorized training review.
31. Apply only the accepted scope; preserve the proposal and supersession
    history.

## 7. Complete one governed change

32. Classify the change's data, tool, authority, and software risk.
33. Run intention → PRD → plan for the bounded slice.
34. Implement on the continuing branch.
35. Run build, lint, tests, browser verification, and any risk-specific gate.
36. Exercise rollback or describe the tested recovery action.
37. Update the program and canonical capability in the same PR if the approved
    policy and executable workflow both changed.

## 8. Close and hand off

38. Re-run all program, projection, docs, build, and test checks.
39. Present the repository and application—not a chat transcript.
40. Name the most consequential remaining gap.
41. Assign 30-, 60-, and 90-day owners, actions, and review dates.
42. Record which source or event should trigger the next program review.

## Recovery ladder

- **App cannot start:** use the completed reference's tested build, then render
  the Markdown directly while diagnosing locally.
- **Client sources unavailable:** retain source names/locations, mark the
  action restricted, and use the fictional trace only for method practice.
- **Too many findings:** complete category roots and one high-risk trace first.
- **Advisor answer is weak:** inspect its citations and answer contract; do not
  switch to an uncited chat answer.
- **Proposed change is not approved:** leave it proposed and demonstrate the
  boundary.
- **Real change overruns:** narrow to the smallest verified slice and preserve
  the remaining work as a named follow-up.
