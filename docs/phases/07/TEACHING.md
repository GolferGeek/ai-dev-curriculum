# Phase 07 — Instructor teaching guide
*Share [OVERVIEW.md](OVERVIEW.md) at open. Learner execution is in
[RUN-ORDER.md](RUN-ORDER.md). The expanded lecture and facilitation live in the
[Phase 07 lesson plan](../../../marketing/lesson-plans/phase-07.md).*

## Teaching outcome

Learners should leave able to operate the AI Program as a company-owned
product: browse it, qualify its authority, find what is missing or stale, trace
one obligation to evidence, prepare a safe change, and use the program to
govern real delivery.

## Room arc

1. **Name the asset.** The take-home product is not only source code. It is the
   organization's accumulated AI direction, decisions, controls, evidence
   pointers, capabilities, and review history.
2. **Separate source from view.** Show the folder README and then the same node
   in the application. Ask which one survives a UI rewrite.
3. **Walk the graph.** Explain all eight categories and the cross-category GRC
   trace. Place technical choices inside governance without turning every
   implementation detail into enterprise policy.
4. **Let the red dashboard teach.** The course baseline is blocked because it
   lacks client authority. Resist the urge to make it green with fictional
   owners.
5. **Ask the six questions.** Inspect scope, sources, ownership, freshness,
   uncertainty, and next action in each answer.
6. **Break a trace.** Remove one link in a disposable branch or specimen and
   ask what must stop. Restore it after the lesson.
7. **Prepare, do not activate.** Generate a proposal and verify that no active
   document changed.
8. **Apply the week.** Complete one low-risk change under the declared risk,
   quality, review, evidence, and rollback controls.
9. **Hand off ownership.** End with named dates and people, not enthusiasm.

## Suggested six-hour schedule

| Block | Minutes | Instructor purpose |
|---|---:|---|
| Product framing and eight-category graph | 35 | establish source-of-truth and governance model |
| Reference-app walkthrough and challenge | 35 | show navigation, findings, advisor, trace, proposal |
| Client repository baseline | 35 | set scope, safety, pre-existing evidence |
| Program adaptation and GRC clinic | 90 | assign authority, preserve gaps, complete traces |
| Governed low-risk change | 105 | apply intention through verified result |
| Readiness challenge and recovery | 25 | test missing/conflicting/stale cases |
| Presentations and 30/60/90 handoff | 35 | transfer ownership and next review |

Add normal breaks outside these contact minutes. If the client needs more
source interpretation, narrow the software change rather than fabricating
governance answers.

## Reference walkthrough

Show these views in order:

1. Overview: eight categories, deterministic counts, course-baseline warning.
2. Folder node: README content, breadcrumbs, status, owner, approval, scope,
   and dates.
3. Findings: exact source paths and distinctions between blockers/warnings.
4. Advisor: “What are we lacking?” followed by an intentionally unanswerable
   client-specific question.
5. Trace: all nine links and the missing owner/approver blocker.
6. Proposal: generated Markdown, no source mutation, explicit review boundary.

Ask learners to find one way the interface could accidentally overstate
authority. Good answers include hiding draft status, compressing uncertainty,
showing an unexplained score, omitting scope, or treating a citation as proof.

## GRC clinic facilitation

Use the client-approved sources gathered before class. For each of three
requirements, have the room state:

- who may interpret it;
- which scope it covers;
- what consequence drives the risk tier;
- which control implements it;
- where enforcement occurs;
- what durable evidence exists;
- who operates, approves, and accepts residual risk;
- what exception is allowed, if any; and
- what date or event triggers review.

One trace should concern data/security, one software delivery, and one client,
contract, audit, or regulatory source. If the third cannot be shared, practice
with the fictional fallback and record the missing real source as the result.

## Challenge pass

Before accepting the capstone, ask:

- Which material is active client policy and who approved it?
- Which source cannot the app see, and how does it avoid overstating certainty?
- Which finding prevents the riskiest action today?
- What would make the answer stale tomorrow?
- Where is the technical enforcement, and what does the evidence actually
  prove?
- Can a project overlay weaken the organization boundary?
- What does proposal generation change? The correct answer is: nothing active.
- Who owns the next review and what event could move it earlier?

## Common failure modes

- Copying the folder tree without replacing or acknowledging placeholders.
- Building a chatbot before defining authority and citations.
- Hard-coding navigation separately from the source hierarchy.
- Hiding incomplete records to make the app appear mature.
- Converting framework text directly into client obligations.
- Calling a Markdown instruction an enforced control.
- Treating an evidence link as proof without inspecting scope and freshness.
- Letting a proposal editor write directly to active policy.
- Spending the day on UI polish while no trace or governed change completes.
- Ending without owners, dates, and follow-up.

## Recovery

If the team cannot use its own repository, adapt the course program and run the
reference app. If the app cannot run, work from Markdown and the deterministic
program checker. If source authority is unavailable, complete the method on
fictional material and preserve the real gap. The non-negotiable learning
outcome is qualified governance reasoning, not a green dashboard.

## Close

> The company does not take home a finished answer. It takes home a system for
> keeping its answers current, owned, evidenced, and challengeable.
